Problem Statement No. 25

📡 What Makes This Project Unique

A deep analysis of the differentiators that set the AI-Powered Signal Quality Analyzer apart from conventional telecom monitoring tools.

🏆 One-Line Summary

This is not just a dashboard — it is a self-contained AI reasoning engine for telecom signal quality that combines real-time anomaly detection, causal AI explanation, multi-model forecasting, and interactive visualization — all runnable with a single command and zero external dependencies.

Core Differentiators

1

IBM Granite as the Reasoning Brain

Unlike rule-based alert systems, this project sends structured context — anomaly counts, severity distribution, interference patterns — to IBM Granite-13b-instruct via watsonx.ai. Granite reasons over the data and returns a structured JSON with root cause, confidence score, and prioritized recommendations. No other open-source telecom monitor does this.

IBM Granite · watsonx.ai
2

Deterministic Offline Mock Fallback

When no API credentials are present, a context-aware mock generates plausible, scenario-specific insights (not generic placeholder text) — distinguishing interference patterns from degradation trends, adapting recommendations to detected events. The app works fully offline with zero configuration.

Zero-credential demo
3

4-Layer Hybrid Detection Engine

Most tools use only thresholds. This system stacks four independent detectors — rule-based thresholds, rolling z-score/EWMA, Isolation Forest, and autocorrelation-based interference detection — then combines their votes into a single severity score. This catches both known and unknown anomaly types simultaneously.

Ensemble anomaly detection
4

Prophet → ARIMA → GBM Forecast Cascade

Three forecasting strategies are tried in order of sophistication, falling back gracefully if one fails. Each metric is forecast independently with 95% confidence bands. BER is log-transformed before fitting — a critical detail missed by generic tools — because BER spans 6 orders of magnitude.

Adaptive forecasting
5

Failure Probability + Time-to-Failure

Rather than just flagging anomalies, the system forecasts when each node will fail and how likely that is. A logistic transform converts breach fraction into a calibrated probability (0–1), and the first forecast step breaching any threshold gives the time-to-failure in hours.

Predictive maintenance
6

Interference Pattern Intelligence

Dedicated interference detection uses autocorrelation analysis to find periodic burst patterns (e.g., every 30 min from co-channel sources) and cross-correlation between SNR drops and BER spikes to identify correlated interference — something no threshold-based system can do.

Signal intelligence
7

5-Scenario Realistic Synthetic Generator

The built-in data generator produces five distinct real-world failure scenarios: normal, gradual degradation, sudden drop, periodic interference, and bursty noise — each with physically accurate signal physics (SNR range, BER log-scale, latency variance). Engineers can demo every feature without real data.

Instant demo · No data needed
8

6 Heatmap Types in One Tab

The Heatmaps tab provides six distinct views: SNR over time, BER (log-scale) over time, latency over time, anomaly density by hour-of-day, severity distribution per node, and row-normalised health KPIs — all with interactive time-bucket resolution and node filtering. This is a richer visual layer than most commercial tools.

Rich visualization
9

Fully Typed, Modular, Tested Codebase

67 unit tests across three modules. Every public function has type annotations. Modules are independently importable — the dashboard calls them directly without an HTTP hop. The API and dashboard share the exact same business logic with zero duplication.

67 tests · 0 code duplication
10

Per-Node Health Score (0–100)

A composite health score is computed for each node using a weighted penalty formula combining anomaly rate, critical/high percentages, and threshold breach rates. This condenses all detection signals into a single actionable number engineers can act on immediately.

Operator-friendly KPI
11

One-Command Local Run + IBM Cloud Deploy

The entire system starts with streamlit run app/main.py. A multi-stage Dockerfile and full IBM Code Engine deployment script (push to ICR → deploy → bind COS) are included and tested — bridging local prototype to cloud production in minutes.

IBM Cloud · Docker · Code Engine
12

REST API Decoupled from Dashboard

A full FastAPI layer exposes all analysis capabilities as REST endpoints, meaning any external system — NOC dashboards, CI/CD pipelines, mobile apps — can consume the same intelligence without the Streamlit UI. The API caches results and supports lazy computation for performance.

FastAPI · 7 REST endpoints
